Build order — every step is something to click

  1. Kickoff on the leader (see §5). Repo cloned, DSH profile projectx exists, empty plugin loads, Captain answers "hello" in OpenBot.
  2. Issues. issue_* tools + markdown store. Captain opens PX-1 and it appears as a file.
  3. Inbox. inbox_post + approval_request. Captain can ask a question without burying it in chat.
  4. Screens. projectx-client takes the root slot: Home · Crew · Issues · Routines · Inbox. Served by dsh --profile projectx web behind Tailscale. From here Oscar uses the browser tab, not OpenBot.
  5. Grok Bot provider. bot_send hands an issue to FillLight Bot; result comes back; Captain is woken.
  6. First routine. Weekly X scout for ASO / Apple Ads / TikTok tactics → digest in Inbox. This is v1 done.

v1 routines for FillLight (after step 6)

  1. Weekly scout — X search for indie-dev ASO / Apple Ads / TikTok tactics; 1-page digest.
  2. Daily numbers — installs + revenue via Grok Bot connectors; flag drops; auto-open a "fix" issue.
  3. Creative pipeline — hooks → script → Postiz draft → approval → publish.
  4. Store watch — App Store Connect status, rejections, reviews → issues.

Not in v1

More than one product · OpenBot as a provider · Stripe · replacing DSH's sidebar for other sessions · mobile-specific UI (the web UI should just work on a phone).

5. Kickoff brief — for the agent on the leader

The Captain already exists on oscar-dev-server-leader as a DSH ACP agent; Oscar talks to it in T3 Code (his daily tool), later in our own UI. Any agent with a shell on the leader reads this section and continues. Read-only first; ask before anything that installs, deletes, or costs money.

What exists (done 2026-11-05 from the Mac over SSH):
  • Repo clone: ~/src/ProjectX
  • DSH profile ~/.dsh/profiles/projectx = dsh-base + dsh-acp-app; its cordis.patch.yml sets the Captain persona and routes the model to cliproxyapi-dev-server / claude-fable-5-1. The key comes from CLIPROXYAPI_DEV_SERVER_API_KEY in the env, via the global ~/.dsh/cordis.patch.yml (never copy it anywhere).
  • Wrapper ~/.local/bin/projectx-acp: cd ~/src/ProjectX && exec dsh --profile projectx. Verified with a raw ACP smoke test: initialize → session/new → prompt → the Captain answers in character.
  • Other facts: user oscar; Ubuntu x86_64, 12 cores, 15 GB; Node 22.23; dsh 0.2.1-rc.5 at /usr/bin/dsh; no pnpm; T3 Code server (t3 serve, port 3773) already running; Hermes on 9119 behind Tailscale / (don't touch); OpenBot, Capy, cloudflared, QuickBook360 dev also running.
  1. Oscar, in T3 Code: Settings → Providers → Add provider → Show more → Local ACP command. Executable: /home/oscar/.local/bin/projectx-acp, no arguments, display name ProjectX Captain. Open a thread on ~/src/ProjectX and say hello. (T3's own doc: providers-acp.md.)
  2. Install pnpm (ask first): npm i -g pnpm. Nothing else global.
  3. Empty bundle. Create packages/projectx-profile with a package.json (dsh.bundle.patch) and a cordis.patch.yml; move the persona there from the profile patch. Model it on @deepseek-ai/dsh-experimental-agent-team-profile. Install with dsh plugin --profile projectx add "link:$HOME/src/ProjectX/packages/projectx-profile". Re-run the smoke test (/tmp/acp-smoke.py pattern) after every change to the profile.
  4. Issues. Create issues/PX-1.md by hand ("Captain reachable from T3", status: done) so the format exists: YAML front-matter key, title, status, owner, product, created, blocked_by, then a markdown body with Acceptance criteria. Then build the issue_* tools in packages/projectx-host (build-order step 2) and add the host package to the bundle.
  5. Our UI (later, build-order step 4). Add dsh-web-app to the profile bundles, run dsh --profile projectx web --no-open --port 3081 --public-url https://oscar-dev-server-leader.<tailnet>.ts.net/projectx/ --trusted-host …, expose with tailscale serve --bg --set-path /projectx http://127.0.0.1:3081. Until then T3 is the window.
  6. Commit often, push to LieuGroup/ProjectX, and update §6 at the end of every session.
